# Feature Specification: 道具配置管理前台

**Feature Branch**: `[003-item-config-frontend]`

**Created**: 2026/06/07

**Status**: Draft

**Input**: User description: "写一个配套的道具配置的前台代码，注意我的前台已经有一个可以跑的框架，在client目录下，你不要另外弄。这个配置主要跟 specs/002-game-item-system 这个目录下的相关文件配套，你理解一下弄就行，不用太复杂"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 查看道具定义列表 (Priority: P1)

管理员进入道具配置页面，看到当前系统中所有已配置的道具定义，以列表形式展示关键信息（名称、类型、品质、堆叠上限），支持分页浏览。

**Why this priority**: 列表查看是管理操作的基础入口，管理员需要先看到现有配置才能决定后续操作。

**Independent Test**: 可以独立测试通过打开道具配置页面，验证列表正确加载并展示所有已配置的道具定义。

**Acceptance Scenarios**:

1. **Given** 系统中已配置20种道具，**When** 管理员打开道具配置页面，**Then** 列表正确展示这20种道具的名称、类型、品质和堆叠上限
2. **Given** 系统中已配置超过50种道具，**When** 管理员浏览列表，**Then** 系统以每页20条分页展示，管理员可翻页查看
3. **Given** 列表正在加载数据，**When** 管理员等待加载完成，**Then** 加载期间显示加载状态提示，加载失败时显示友好错误信息

---

### User Story 2 - 创建新道具定义 (Priority: P1)

管理员点击创建按钮，填写道具的基本信息（名称、描述、类型、品质、堆叠上限等），根据所选类型填写对应扩展信息（消耗品效果或装备属性），提交后系统保存新道具定义。

**Why this priority**: 创建新道具是运营内容更新的核心操作，直接影响游戏内可投放的道具种类。

**Independent Test**: 可以独立测试通过填写完整信息并提交，验证新道具定义成功保存并在列表中可见。

**Acceptance Scenarios**:

1. **Given** 管理员填写了完整的道具信息（名称、类型为消耗品、品质、堆叠上限、消耗品效果），**When** 管理员提交创建，**Then** 系统保存成功，新道具出现在列表中
2. **Given** 管理员选择道具类型为"装备"，**When** 管理员继续填写表单，**Then** 界面动态显示装备专属字段（装备属性、装备部位），隐藏消耗品效果字段
3. **Given** 管理员填写表单时遗漏了必填项（如道具名称），**When** 管理员尝试提交，**Then** 系统提示具体遗漏项，阻止提交并保留已填写内容
4. **Given** 管理员填写的堆叠上限小于1，**When** 管理员尝试提交，**Then** 系统提示堆叠上限必须大于等于1

---

### User Story 3 - 编辑道具定义 (Priority: P1)

管理员在列表中选择某个道具，点击编辑，系统加载该道具的当前配置到表单中，管理员修改后提交更新。

**Why this priority**: 道具属性调整是运营调优的常见需求（如平衡装备数值、修正描述错误），需要支持快速修改。

**Independent Test**: 可以独立测试通过编辑某个现有道具并提交，验证变更正确保存且列表中实时反映更新。

**Acceptance Scenarios**:

1. **Given** 管理员选择编辑一件已存在的装备，**When** 编辑页面打开，**Then** 表单中预填充该道具的所有当前配置信息
2. **Given** 管理员修改某装备的基础攻击力并提交，**When** 更新成功后，**Then** 系统提示保存成功，列表中该道具信息同步更新
3. **Given** 管理员在编辑过程中误操作关闭了页面，**When** 管理员重新打开编辑，**Then** 系统从服务器加载最新配置，不保留上次未提交的本地修改

---

### User Story 4 - 删除道具定义 (Priority: P2)

管理员在列表中选择未被任何玩家持有的道具，执行删除操作；若道具已被玩家持有，系统阻止删除并提示原因。

**Why this priority**: 清理未使用的测试配置或过期道具定义是维护需求，但发生频率低于增改操作。

**Independent Test**: 可以独立测试通过尝试删除不同状态的道具，验证删除权限判断正确。

**Acceptance Scenarios**:

1. **Given** 某个道具定义没有任何玩家持有，**When** 管理员执行删除并确认，**Then** 系统删除该定义，列表中不再显示
2. **Given** 某个道具定义已有玩家持有，**When** 管理员尝试删除，**Then** 系统提示"该道具已被玩家持有，无法删除"
3. **Given** 管理员点击删除按钮，**When** 系统弹出确认对话框，**Then** 管理员可以选择取消操作，取消后数据保持不变

---

### User Story 5 - 筛选与搜索道具定义 (Priority: P2)

管理员在列表上方使用筛选条件（类型、品质）或关键词搜索，快速定位目标道具。

**Why this priority**: 当道具数量较多时，筛选和搜索能显著提升管理效率，属于体验优化功能。

**Independent Test**: 可以独立测试通过组合不同筛选条件和关键词，验证列表正确过滤展示。

**Acceptance Scenarios**:

1. **Given** 系统中存在多种类型的道具，**When** 管理员选择筛选条件"仅看装备"，**Then** 列表只展示类型为装备的道具
2. **Given** 管理员在搜索框输入"生命药水"，**When** 执行搜索，**Then** 列表展示名称包含"生命药水"的道具
3. **Given** 管理员同时设置了类型筛选和关键词搜索，**When** 执行查询，**Then** 列表展示同时满足两个条件的道具

---

### Edge Cases

- 管理员在创建/编辑表单中输入超长名称或描述，系统如何限制和提示？
- 网络异常导致提交失败，系统如何保留用户已填写的内容？
- 两名管理员同时编辑同一道具定义，后提交的管理员是否会覆盖前者的修改？
- 管理员快速连续点击提交按钮，系统如何防止重复创建？
- 列表数据量很大（如上千条），前端如何保持流畅的筛选和翻页体验？

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须支持以列表形式展示所有道具定义，每行展示名称、类型、品质、堆叠上限等关键信息
- **FR-002**: 系统必须支持分页浏览道具定义列表，每页默认展示20条记录
- **FR-003**: 系统必须支持管理员创建新道具定义，表单包含：名称、描述、类型、品质、图标标识、堆叠上限、等级要求、绑定属性，以及根据类型动态展示的扩展字段
- **FR-004**: 创建和编辑表单必须对必填项进行前端校验，并在提交前阻止不完整数据的提交
- **FR-005**: 系统必须支持管理员编辑已有道具定义，编辑页面加载时预填充当前数据
- **FR-006**: 系统必须支持管理员删除未被任何玩家持有的道具定义，已被持有的道具不可删除
- **FR-007**: 系统必须支持按道具类型（消耗品/装备/材料/任务道具）筛选列表
- **FR-008**: 系统必须支持按道具品质筛选列表
- **FR-009**: 系统必须支持按道具名称进行关键词搜索
- **FR-010**: 所有创建、编辑、删除操作必须给出明确的成功或失败反馈提示
- **FR-011**: 表单中道具类型选择后，必须动态切换对应的扩展字段（消耗品效果或装备属性/部位）
- **FR-012**: 列表和表单中涉及枚举值（类型、品质、装备部位）的展示必须使用中文标签而非原始编码值

### Key Entities *(include if feature involves data)*

- **道具定义（ItemDefinition）**: 管理员通过前台维护的道具模板数据，包含名称、描述、类型、品质、图标、堆叠上限、等级要求、绑定属性、消耗品效果、装备属性及部位
- **消耗品效果（ConsumableEffect）**: 道具定义中的子结构，包含效果类型、目标属性、数值、持续时间
- **装备属性（EquipmentStats）**: 道具定义中的子结构，包含攻击力、防御力、生命值上限等加成数值

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 管理员可以在3秒内打开道具配置页面并看到加载完成的列表
- **SC-002**: 管理员完成一次新道具创建的完整流程（填写+提交+确认）平均耗时不超过2分钟
- **SC-003**: 列表筛选和搜索的响应时间在1秒内返回结果
- **SC-004**: 表单提交后，系统在2秒内给出成功或失败的明确反馈
- **SC-005**: 管理员在列表中定位任意道具所需的平均操作不超过3次（搜索/筛选/点击）

## Assumptions

- 管理员已通过现有系统的认证机制登录，前台仅处理已认证管理员的操作
- 道具配置前台集成在现有客户端框架内，作为独立的功能页面存在
- 后端数据接口由 002-game-item-system 提供，前台通过标准接口进行数据交互
- 道具图标资源的管理（上传/预览）不在本版本范围内，仅通过标识符选择或文本输入
- 表单中枚举字段（类型、品质、装备部位）的选项集与 002-game-item-system 定义保持一致
- 本前台仅面向管理员使用，不考虑普通玩家的访问权限和体验
